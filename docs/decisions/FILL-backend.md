# FILL-backend — connect the facts and the testing to the account pages

Stage: backend. Problem: 131 of 158 account pages rendered as dashes, knockouts were labelled
`commercial_property`, the peer Verdict column was blank, and the verification results were not
connected to any account.

| # | Decision | Why | Rejected alternative |
| --- | --- | --- | --- |
| D1 | **The triage query also reads the display facts** — insured, broker and underwriter names, requested limit, received and target effective dates, status, decline reason, competitor, line — for all 158 submissions. Still ONE query. The references are resolved with `$expand` select leaves (`insured: { $expand: { select: ['name'] } }`), exactly the form QUERY_REQUEST_BODY.pdf documents, with no `expand` stage. The trace step carries a second `requiredBy` entry, `PRD-10-ACCOUNT-FACTS`, and its goal says why. | The facts already sit on the Submission record the triage reads; a second query would cost a round trip and learn nothing new. PRD 7.3: "the `$expand` leaf when it is only wanted in output" — these names are display-only. Contact is not fetched: nothing on the page needs it and the outbox already reaches the producer contact through the follow-up. | A separate facts query per knockout (120 round trips), or an `expand` stage (hydrates the full records for no downstream reader). |
| D2 | **Facts are stored in a new nullable `submissions.facts` column, never fed to the engine.** The knockout bundle keeps its four fields, so every score, rank and golden pin is unchanged. `migrate` adds the column to an existing database with `ALTER TABLE ... ADD COLUMN` when `PRAGMA table_info` lacks it. Idempotent ingest backfills facts onto rows it skips (no re-score, `updatedAt` untouched), and `seed --if-empty` now also seeds when a Federato row has no facts — so the Railway volume fills in on the next boot without `--force`. A row with no facts is served as `source: 'not_fetched'` with every value null. The insured name falls back to the facts' name where the broker record has none (the 120 knockouts), so the queue names them too. | Stuffing the facts into the raw bundle would feed them to `discover`/`normalize` and could move scores; an undeclared key in the `raw` JSON blob would be invisible to the type system. The frozen-schema rule is overridden by this stage's ownership of `apps/api/src/**`. | Re-scoring knockouts with the new fields. |
| D3 | **If the handler rejects the triage projection, the planner retries once with the old four-field select** (`adapt_retry`, adaptation `minimal_select`, linked by `adaptedFrom`), warns, and carries on with the facts absent. | The `$expand` leaf is documented but was never exercised against the live handler (the snapshot mock implements it). A rejected triage would store nothing at all; the fallback keeps the book intact and says so. | No fallback. |
| D4 | **`accountKind`** on the detail and queue row: `triage_knockout` (knocked out on line of business), `no_policy` (a Federato row whose bundle has no Policy record), else `scored`. **`displayLineOfBusiness`** is Federato's own line (facts first, then the raw record) for a knockout, otherwise `lineOfBusiness`. `lineOfBusiness` keeps its meaning — the spec the account is scored on — because `vectorSpec` and the console's labels key off it. | The console needs to choose the view without re-deriving it. | Changing `lineOfBusiness` to a free string, which would break its typed use as a spec key. |
| D5 | **`packages/verify/src/scripts/per-account.ts` writes `per-account.json`**, keyed by submission id: the naive oracle's verdict, score, knockouts and deciding factor with an agreement flag for each, and layer C's verdict, deciding factor and reasoning from the committed `layer-c.json` (never re-run). It reuses `real-inputs.ts`'s rollup, now exported as `realInputs()`, so layer B and layer C read identical facts. The naive side is compared with the engine's full `runEngine` result on the real account (as of its received date), not with a vector-level re-run. The committed file is pinned by a test that rebuilds it and compares. | The API cannot import `@retrofit/verify` (verify depends on api). Result: 38/38 naive agreement on all four, 38/38 layer-C verdict agreement. | Importing verify from api (a cycle); re-running layer C (costs model calls, needs a key). |
| D6 | **`verification.matchesCurrentResult`** compares the stored result the page shows with the verified engine outcome (verdict equal, score within 1e-6). All 38 match on the current snapshot. | The API scores as of today, the verification ran as of each received date, and a broker reply re-scores an account. The page must not present a verification of a result it no longer shows. | Assuming they always match. |
| D7 | **`GET /verification`** (route table + frozen `app.ts`, both edited as this stage's task allows) parses, at request time: `run.json` (layers A+B), `layer-c.json` (agreement with its interval, per-stratum table, every disagreement with both sides, deciding-factor agreement, unanswered count), `per-account.json` (real-account summary), `summary.json` (extraction accuracy, null), VERIFICATION.md (the extraction reason: its sentences up to — never including — the first that carries a score, plus "To measure it"), and DECISIONS.md (CP1 counts, Run 2 confirmed/refuted, and the rows CP1-2, CP1-4, CP1-5, R2-1…R2-8 as `{id, phase, title, detail}`). No number is written in code; a missing file makes its block null; a corrupt file throws. A test asserts the discarded 41% never appears. | The console showed headline tiles only. Parsing the committed files keeps one source of truth. | A hand-maintained JSON of defects, which would drift from DECISIONS.md. |
| D8 | **Peer verdicts are attached at read time in the detail route**, from each peer's own stored result — the result the same book re-score wrote. `result.peers` is left untouched; the detail's `peers` is `PeerResultDto` (each match plus `verdict: Verdict \| null`). `packages/engine/src/stages/peers.ts` is not changed. | At read time the verdict is always the one the peer's own page shows, even after a single-account re-score (a reply) that did not re-run the others. Persisting it into each result would go stale. | Adding `verdict` to the engine's `PeerMatch` (a frozen engine type) and writing it into every stored result. |
| D9 | **A per-account verification file that cannot be read leaves the block null on the account page**, while `/verification` throws on it. | A corrupt verification file must not take down every account page; the dedicated endpoint is where the error surfaces. | Failing the detail route. |

## For the orchestrator

- The live Railway volume holds rows stored without facts. The next boot's `seed --if-empty` now sees that
  (`needsSeed`) and runs one idempotent ingest that only backfills facts — no re-score. A `--force`
  re-seed also works.
- The triage `$expand` leaves have not been sent to the live handler (no network in this stage). If it
  rejects them the trace shows a `minimal_select` retry and the facts come back `null`; the book is still
  triaged.

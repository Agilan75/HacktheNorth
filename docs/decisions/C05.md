# C05 — SubmissionPage decisions

1. **The page owns the panel frame.** Each of the twelve PRD 10 panels is wrapped in the C02 `Card` with title `(a) Explanation and recommendation` … `(l) Attached photo or sweep` and `anchorId="panel-<letter>"`, plus an in-page index nav. Panel components (C06–C11) render content only. Rejected: letting each panel draw its own Card — twelve units would each invent a heading and anchor scheme. If a panel also draws a Card the result is a nested card, cosmetic only.
2. **(d) and (k) are composite.** (d) = `Pricing` then `PeerBenchmark`; (k) = `Actions` then `ReplyBox`. The PRD lists both halves under one letter.
3. **Per-panel error boundary.** A private `PanelBoundary` catches a render error in one panel and shows it inline (`role="alert"`), so one broken panel never blanks the other eleven. It resets when a new detail object arrives.
4. **No recomputation.** The header shows `verdict`, `appetiteScore` (`81/100`), `completeness` (0–100, one decimal: `88.9%`), `confidence` (ratio: `70%`) straight from the DTO through `@retrofit/contracts` formatters. Panels receive DTO slices by reference.
5. **Mutations.** Re-run (`runSubmission`) and Enrich (`enrich`) display the detail they return without a refetch; approve and reply call the API then `reload()` the GET so before/after numbers come from the server. Reply result is held in page state and passed to `ReplyBox`. Mutation failures render as an alert; buttons disable while one is in flight.
6. **No colocated test in the tree.** C05 owns only `SubmissionPage.tsx`; creating `SubmissionPage.test.tsx` would write outside the owns list. The test was run from the scratchpad against the real page (7/7 pass) and its text is in `docs/contracts/requests/C05.md` for the human to place.

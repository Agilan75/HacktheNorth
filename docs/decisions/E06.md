# E06 — decisions (evaluate + verdict)

Unit E06 owns `packages/engine/src/stages/evaluate.ts` and
`packages/engine/src/stages/verdict.ts`. Everything INTERPRETATIONS.md fixes is
implemented literally (T-BLANK, T-SPAN, G-2/G-3, R-AGE-REFER, V-1..V-9). The
four items below were genuinely open and are decided here.

## D-1 — the factor tier value is read from `vector.t`, not re-derived from rules

`FeatureVector.t` already carries the tier value per component (E05 `tiersFor`),
and T-SPAN says every component of a factor carries the same value. `evaluate`
therefore takes `tierValue` from the factor's components and uses the rulebook
only for the *label*, the citation and the knockout/refer attribution.

Rejected: recomputing the tier from the fired rules. That would give two
implementations of §3 inside one engine and let `evaluate` and `vectorize`
disagree silently.

T-BLANK is still applied defensively in `evaluate` (`acceptable → 1` on the four
blank-Target factors). It is idempotent, so it changes nothing when the vector
already carries it, and it stops a hand-built vector scoring 0.6 on
`construction_type`.

## D-2 — which fired rule "decides" a factor

Several rules can fire for one factor (`AG-TIV-T` and `AG-TIV-A` overlap by
construction, because conditions are AND-only and cannot say "and not Target").
The deciding rule is chosen by: (1) the rule whose tier value equals the
factor's tier value, then (2) Not Acceptable before Target before Acceptable
(INTERPRETATIONS 3.4's stated order of evaluation), then (3) rulebook order.
A `refer` rule is never a deciding rule (G-10: a flag, not a score).

## D-3 — V-7 confidence over a `rollup.*` field

V-7 says the confidence is the product of the source confidences of the fields
the deciding rule used. A rollup value (`rollup.totalTiv`, `rollup.pctTivPre1990`)
has no provenance of its own; it is computed from up to 129 building slots.
Multiplying 0.7 by itself 129 times reports confidence 0, which is wrong and
would make the number useless.

**Decision:** a `rollup.*` path contributes **one representative field per
distinct provenance source kind**, not one per record. So an all-broker-typed
account decides at 0.7, and an account whose `yearBuilt` is public record and
whose `tiv` is broker-typed decides at `0.9 × 0.7 = 0.63`. The per-record
mapping lives in `ROLLUP_CONTRIBUTORS`, private to `evaluate.ts`. Direct
canonical paths (`pricing.quotedPremium`, `submissionType`) contribute their
`bestValue` field exactly once, deduped by path.

Rejected: (a) one field per record — collapses to 0; (b) the mean of the
contributing confidences — not a product, contradicts V-7's wording.

## D-4 — an extension refer rule still raises REFER

`referFactors` is typed `readonly AppetiteFactorId[]`, so an extension rule on
`sprinkler_protection` cannot appear in it. V-4 says "a fired refer rule",
without limiting it to the eight factors, and PRD 6.6 says extensions "can raise
REFER". `verdict` therefore checks `referFactors` **or** any fired rule with
`tier: 'refer'`. Extension rules still contribute 0 points and never knock out.

## D-5 — `interpretationsApplied`

An interpretation is surfaced when its `affects` list names a condition field
(or that field's canonical source path) of a rule that actually fired, deduped
by id, rulebook order then extensions order. I-3's narrower "only when the tier
depends on the assumed-acceptable buildings" test needs
`rollup.pctTivByConstruction`, which E03 produces but no rule condition reads;
if E13 encodes that dependency as a condition, this rule surfaces it unchanged.

## D-6 — `missingComponentKeys` and `reasons`

`missingComponentKeys` lists **every** missing component, required or not, in
spec order: the console shows optional gaps too, and V-2's completeness test
already reads only the required nine. `reasons` are generated by code (never by
an LLM), deciding factor first, then other knockouts, then completeness, then
open HIGH contradictions, then referrals.

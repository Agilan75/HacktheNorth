# A16 — ingest + rescore services

## D1 — Stored `canonical` is broker data; enrichment merges on every run
`submissions.canonical` holds the normalized record (plus answers the reply service
writes into it). Enrichment values stay in `enrichments` and are merged by
`runEngine` each run, de-duplicated by (path, value, source, sourceDetail) together
with `RescoreOneInput.extra`. `extra` is not persisted: a non-enrichment value that
must survive a later `rescoreBook` has to be written into `canonical` by its owner.
Rejected: storing `result.canonical` back — every re-score would re-merge the same values.

## D2 — BookStats and peers per line of business; peers commercial only
The commercial and tenant vectors are different lengths and meanings. Peers run
for commercial property only (PRD 6.4 peers are account benchmarks). A candidate
with no quoted premium (no policy) is passed as `reduceForCoarseMatch(vector)`,
`coarse: true`. Rate = premium / (TIV/100); annual loss = fiveYearLoss / 5,
matching `computeBookStats`.

## D3 — Rank is per line of business, written to `submissions.rank`
1-based within the account's own queue. `result.id` is forced to the row id so
rank entries map to rows regardless of how the canonical id was minted.

## D4 — Two engine passes
Pass 1: `runEngine` with `bookStats: null`, no peers, to get every vector (stage 6
needs no stats). Then `computeBookStats` over the whole line. Pass 2: full engine
with the stats and every other account as a peer candidate. `rescoreOne` uses the
other accounts' stored vectors (fresh pass-1 vector when missing or on another
spec version), stores only the target's result, then re-ranks the line.

## D5 — Explanation stored without the rank
`result.explanation = explain({ result, insuredName }).text` (federato template,
deterministic). The rank is left out so the text never goes stale when another
account moves. A template throw leaves it `null`.

## D6 — Ingest
- Row id = `externalId` for new rows; existing rows keep their id and createdAt.
- Idempotency: an external id whose row already holds a `canonical` is skipped
  unless `force`. Only touched rows (or any row lacking a result) trigger `rescoreBook`.
- Triage knockouts (other lines of business) are counted, not stored:
  `LineOfBusiness` has no value for them.
- `lineOfBusiness: 'tenant'` returns an empty response with a warning.
- No schema-assist LLM call is passed to the planner: ingest stays fully
  deterministic; unmapped fields remain visible as planner warnings.
- High-scorer follow-up (PRD 7.5 step 5): touched accounts that are not knocked
  out after the first score get `runFollowUps`; followed-up bundles are
  re-normalized and the book is re-scored once more.
- Requested external ids that did not come back produce a warning naming the
  triage reason when there is one.

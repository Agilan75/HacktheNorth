# E17 — decisions (real fixtures, frozen commercial rating table, golden test)

## D-1 — `realCases()` reads the committed snapshot with `readFileSync`
The engine cannot import `@retrofit/federato` (federato depends on engine; a
cycle) and cannot JSON-import across `rootDir: src`. So `fixtures/real.ts`
reads `packages/federato/snapshot/{snapshot.json,policy-property-hydrated.json}`
and `vectors/commercial.json` from disk, resolved from `import.meta.url`, and
memoizes. It is fixture/CLI support (used by `rating:fit` and tests), never by
a stage, so stage purity is untouched. Rejected: copying the snapshot into
`packages/engine` (two copies drift).

## D-2 — bundles mirror F09 `toBundles` exactly
Policy case: `records.Policy = [hydrated row]`, schema + fetchedAt from the
snapshot. No-policy case: `records.Submission = [row]` with `insured -> hq` and
`broker` expanded from the flat snapshot records, which is what the live
no-policy follow-up returns. No-policy set = property submissions with status in
lost/cleared/quoted/declined/received and no Policy row: exactly 11
(4 lost, 3 cleared, 3 quoted, 1 declined). Order: policies then no-policy, each
sorted by submission number. Then `discover` + `normalize` (E02), nothing else.

## D-3 — the fit was run as-is and frozen
`rating:fit --fitted-at 2026-09-19T14:05:01.294Z` (the snapshot's fetchedAt, so
the file is reproducible and no clock is read). 27 policies, 117 buildings;
policy MAPE 27.8%, R² 0.724 (PRD 6.7 quotes R² 0.72 for premium~TIV). The
golden test re-runs the CLI in dry-run and asserts byte equality with the file.

## D-4 — golden verdicts pinned from the first full real run
26/27 policies are DOES_NOT_FIT (state tier, premium-high, age, ST rules), one
REFER (AG-TIV-A-LOW); all 11 no-policy accounts REFER (missing data). This is
the dataset, not a normalization bug: construction/state/age inputs were
spot-checked against the raw snapshot. A change to this table is a behaviour
change on real data.

## Observed, not mine to fix
- Every policy's five-year loss is 0 or null: its claims all fall AFTER its
  received date, so the window (measured back from receivedDate) excludes them.
  The loss bands above $25K therefore sit on their priors.
- 4 policies with `claims: []` get `fiveYearLoss = null` (not known 0) because
  F09-shaped bundles carry no `records.Claim` key and E03 D6 reads that as
  "claims never fetched", though the deep query did expand claims. Fixing it is
  an F09 (add `Claim: []` when the hydrated policy carried a claims array) or
  E03 decision; E17 mirrors runtime and does not paper over it.

# F09 — plan + to-bundle decisions

Owns `packages/federato/src/planner/plan.ts` and `to-bundle.ts`. Deep pass is the
verified LIVE_DATA_FACTS `Policy` query verbatim; no payload ever carries `over`
or a reduction (tested).

## D1 — External id fallback
`externalIdOf` returns `submission_number`; for a policy row it reads the
expanded `submission` object. When no number exists it returns
`submission:<numeric id>` (both for a bare Submission row and an un-expanded
Policy row's `submission` reference), so the two always agree. A record with no
identity throws; callers (`triageRows`, `toBundles`) skip such rows.
Rejected: `SUB-<id>` — would fabricate a number the data never contained.

## D2 — Missing line of business survives triage
Per G-2/G-3 a missing component never knocks out, so a triage row with a null
`line_of_business` survives and falls through to the no-policy pass / REFER.

## D3 — Tenant line
`tenant` has no Federato line. Triage knocks every row out (`AG-LOB-NA`);
`planDeep`, `planFollowUps` and `buildPlan().deep` are null/empty.

## D4 — No-policy query targets ids, not statuses
`where: { id: { $in: [...] } }` with `expand { insured: { hq }, broker }`.
Rejected: the status list from LIVE_DATA_FACTS — it returns the same 11 today
but would silently include/exclude rows if a status changed; ids are exact.

## D5 — Deep pass filters on line, not survivor ids
`where: { line_of_business: <line> }` exactly as verified live. Filtering by
`submission $in ids` is unverified against the live handler. `toBundles`
orders by survivors and appends any unlisted hydrated account rather than
dropping it.

## D6 — High-scorer follow-up is one Policy query
Expands `submission, coverages, endorsements, producer { broker, contact }` and
filters `submission.submission_number $in ids` (a single reference, so the
dot-path is legal after expand). Its rows are appended under `records.Policy`
of the matching bundle; the engine dedups entities by group:id.
Rejected: a separate broker-history Submission query — broker ids are unknown
at plan time and PRD §7.5 step 5 says "one further query".

## D7 — `buildPlan(input)` is the pre-result skeleton
With no rows it cannot triage, so it returns the triage query and the deep
query (empty `expectedExternalIds`), with no-policy/follow-ups/knockouts empty.
F11 composes the live plan from `triageRows`, `planDeep`, `planNoPolicy`,
`planFollowUps` as each pass returns.

## D8 — Survivor with no returned row
Still gets a bundle, whose `records.Submission` is its triage row (id, number,
status, line), so it resolves to REFER with missing data instead of vanishing.

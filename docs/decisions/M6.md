# M6 — /sweep and /analyzing

Files: `apps/mobile/app/sweep.tsx`, `apps/mobile/app/analyzing.tsx`. Typecheck (`npx tsc -p apps/mobile --noEmit`) is clean for both. The only errors left are the known `packages/engine/src/data.ts(54)` URL error and one in M9's `hazard/[id].tsx` (`BORDER` is not exported from `@/ui`), and neither is mine.

## Decisions

| # | Decision | Why | Rejected |
|---|---|---|---|
| M6-1 | **No new `src/lib` module and no tests file.** The only pure logic here is the stage-to-step mapping and the permission gate, and both are kept private in the screen files. | M6 owns only the two route files. Everything testable that they rely on (capture reducer, heading filter, session, API client, poll, queue) is already covered by M1 and M2's vitest suites. | Creating `src/lib/analyzing.ts`, which would be outside my ownership. |
| M6-2 | **/sweep sends the sweep itself** through M1's `getSweepQueue`, then does `router.replace('/analyzing', { id })`. This matches what M5's `/new` does for its upload path. | M5's header comment says "/sweep (M6) captures and sends". /analyzing then only ever deals with a sweep id. | Sending from /analyzing. |
| M6-3 | **Permission flow.** A plain-language primer ("stand in the middle, hold upright, turn slowly, the phone takes the photos") comes before the system dialogs, with the photo path as an equal button. If the camera is refused, the screen explains, offers "Allow the camera" (or "Open Settings…" when iOS will not ask again), and makes "Use 3 photos instead" the **primary** button. Both permissions are read again when the app comes back from Settings. | PRD §11 inclusivity: the photo path has to be a real way through, not a hidden fallback. | Asking with no explanation first. |
| M6-4 | **Location refused does not block on its own.** We still call `watchHeadingAsync` (magnetic heading does not need true north). If no reading arrives within 6 s, or the watch errors, the screen shows "The compass is not working", explains why in plain words (location off, or metal nearby / figure-8), and offers photos first, then Settings, then "Try the compass again". | iOS behaviour on heading without location authorisation varies. A watchdog decides from what actually happens rather than guessing. | Treating location refused as a hard stop. |
| M6-5 | **The machine starts** (`dispatch start`) only once the camera has fired `onCameraReady` AND the first filtered heading has arrived. The first frame is taken right away, where the person is facing. | `takePictureAsync` must wait for camera ready, and bearings are relative to the first heading. | A "Start" button (one more step, and the primer already explains what to do). |
| M6-6 | **Capture:** `takePictureAsync({ quality: 0.8, shutterSound: false })`, then `manipulateAsync` resize to a 768 px long edge, JPEG 0.7, base64 (the prototype's encoder). Then one `Haptics.impactAsync(Light)` per frame, and `captured` is dispatched. Image data lives in a ref keyed by the machine's frame index, not in reducer state. On any error, `captureFailed` is dispatched and the next heading sample retries (M2-6). The shutter animation and sound are off. | A tick per frame is the PRD cue. Clicking 15 times while turning is noise, and a flash hides the preview. | Keeping the shutter sound on as the capture cue. |
| M6-7 | **Pitch** comes from `DeviceMotion` `rotation.beta` as `beta° - 90` (0 = upright, -90 = camera at the floor), sampled at 200 ms and attached to each frame. It is optional: without it, frames carry no pitch. | The API accepts `pitchDeg` and the ring does not use it. | Blocking the sweep on motion permission. |
| M6-8 | **"Use 3 photos instead" lives on /sweep too** (the overlay button and every problem screen). It runs the same picker as M5 (3 photos, ordered, bearings from `uploadBearings`), downscales with the same encoder, then sends. The encoder is duplicated privately rather than imported from `app/new.tsx`. | AGENTS §7 says no invented shared helpers, and a route file is not a library. | Sending people back to /new, which would lose their place. |
| M6-9 | **The overlay sits in a `ScrollView`** over the full-screen `CameraView`. | M4's checklist warns that at AX5 the bottom panel can run off-screen. | A fixed View. |
| M6-10 | **/analyzing reads the stage only from the server.** It uses M1's `pollSweep` (1.2 s). The server's `stage` names the last step it *finished* (services/sweep.ts), so N finished steps = `ORDER.indexOf(stage) + 1`. Each step shows a ✓ / spinner / ○ shape plus "Done / In progress / Waiting", so the state is never shown by colour alone. VoiceOver hears one line per finished step, never one per poll. | Task: no fake timer. | Animating steps on a timer. |
| M6-11 | **Resting stages:** `questions` goes to `/confirm?id` (M7 moves straight on to /questions when there is nothing to confirm). `done` goes to `/verdict?id`. `failed` shows the server's `error` when it is plain words. A technical one (`"observing: …"`) is swapped for a generic sentence. Then "Scan the room again" and "Use 3 photos instead". Navigation uses `replace` so Back never lands on the loader. | Plain language, and no dead ends. | Showing raw server errors. |
| M6-12 | **Coverage too low (PRD §9.3 "re-sweep of the named arc").** When the API's `coverage.sufficient` is false, only for a *camera* sweep, the screen stops before moving on. It names the missed part in words ("about 90 degrees to the right of where you started", from the API's `largestGap`) and offers "Scan the room again" or "Continue anyway". Uploaded photos are never asked to re-scan. | Three photos rarely reach 75%, and the photo path must never loop. | Forcing a re-scan. Prompting uploaders. |
| M6-13 | **Facts shown during analysis** are read straight off the SweepDto: photos kept (frames not `dropped`), the API's `coveragePct` rounded, and the number of observations. Nothing is computed. | The API decides every number, and the screen only counts and rounds what it returns. | — |
| M6-14 | **Poll timeout** (M1's 3 min limit) shows "This is taking longer than usual" with "Keep waiting", which restarts the poll. Other errors show `describeApiError` with "Try again". | — | — |

## Human checklist (iPhone, Expo Go). None of this has been run on a device.

1. **Primer:** New sweep → name a room → Scan. Pass: "Before you scan" with 3 numbered steps, "Allow camera and compass" and "Use 3 photos instead" both full width. Tap Allow. Pass: the Camera dialog, then the Location dialog, and no "camera is off" screen flashes behind them.
2. **Camera preview + ring:** Pass: the live back-camera picture fills the screen, the ring and % are at the top, the hint and Finish are at the bottom.
3. **Auto-capture + haptic:** Hold upright and turn slowly. Pass: a light tap roughly every 1–2 s while turning, no tap while standing still, no shutter sound or flash. "Photos: N of 15" climbs and stops at 15 while the ring keeps filling.
4. **Compass direction:** turning right (clockwise) fills the ring clockwise from the top. If the ring does not fill at all while you turn with the phone held upright, the iOS heading is not following the camera direction when vertical. Record it (it would need the tilt-compensated heading).
5. **Finish:** it stays locked below 75%. At 75% or more, tap Finish. Pass: "Sending N photos…", then "Working it out". The API log shows `POST /sweeps` with N frames, and each frame is about 768 px on the long edge (check a frame's size in the API log/DB if possible).
6. **Camera refused:** Settings → Expo Go → Camera off, then open /sweep. Pass: "The camera is off for this app" in plain words, "Use 3 photos instead" is the top (red) button, and "Open Settings…" opens Settings. Turn the camera back on, come back. Pass: the screen moves on to the camera by itself.
7. **Location refused:** Settings → Expo Go → Location: Never. Pass: either the scan still works (the heading arrived), or within about 6 s you see "The compass is not working" with photos as the top button. It never hangs.
8. **Photos from the scan:** mid-scan, tap "Use photos instead" and pick 3 photos. Pass: sending, then /analyzing. Cancel the picker. Pass: the scan carries on.
9. **Analyzing is real:** watch the steps. Pass: the ticks move in step with the API log's stage changes, not on a steady beat. It then lands on "Check what we found" (or "Your quote"). Back does not return to the loader.
10. **Failure:** sweep a dark cupboard, or point at a blank wall. Pass: the server's plain reason ("No frame passed the photo-quality check…") plus "Scan the room again" and "Use 3 photos instead".
11. **Low coverage:** Finish at exactly 75% with several blurry frames. If the API reports insufficient coverage, you see "Part of the room did not come out clearly: the part about N degrees to the right…" and the two choices.
12. **Offline:** Airplane Mode, then Finish. Pass: "Waiting for a connection" and the queued message. Turn Airplane Mode off (or tap "Try sending now"). Pass: it moves on to /analyzing by itself.
13. **VoiceOver:** every button reads a clear label. /analyzing reads "Step 2 of 5: Photos checked, done". Completed steps are announced once each.
14. **AX5 text size:** on /sweep, the bottom panel scrolls instead of being cut off. On /analyzing, steps wrap and nothing overlaps.
15. **Grayscale:** step states can be told apart (✓ / spinner / ○ plus words).
